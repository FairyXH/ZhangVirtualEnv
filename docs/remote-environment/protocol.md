# Remote Environment Protocol v1

通用远程环境数据总线协议。协议不绑定 ESP32；ESP32、Linux、Windows、Android
或其他采集器都可以作为 Collector 接入。服务器负责认证、设备注册、缓存、路由和
订阅，不负责解释所有 `data` 内容。

## 1. Transport

- WebSocket endpoint: `/ws`
- Production: `wss://<host>/ws`
- Development: `ws://<host>/ws`
- Text frames are UTF-8 JSON objects.
- Maximum accepted JSON message size: 1 MiB by default.
- A connection must authenticate before using device or environment operations.

## 2. Common envelope

Every application message has a `type` field. Environment payloads use:

```json
{
  "version": 1,
  "device_id": "esp32-001",
  "data_type": "bluetooth",
  "timestamp": 1755745200123,
  "sequence": 18291,
  "data": {
    "raw": "...",
    "devices": []
  }
}
```

Rules:

- `version`: protocol version, currently `1`.
- `device_id`: logical device identity; it is not a token.
- `data_type`: extensible lower-case identifier. v1 defines `bluetooth`, `wifi`, and
  `cell`; future values such as `gnss`, `sensor`, and `nfc` do not require transport changes.
- `timestamp`: Unix epoch milliseconds generated by the collector.
- `sequence`: monotonically increasing per device and data type. The server rejects
  malformed values and may drop an older sequence without closing the connection.
- `data`: type-specific JSON object. Unknown fields and `raw` data are preserved.

## 3. Roles and authentication

### 3.1 Android consumer

```json
{ "type": "auth", "role": "consumer", "token": "..." }
```

The token identifies a permitted consumer session. The server replies:

```json
{ "type": "auth_result", "success": true, "role": "consumer", "server_time": 1755745200123 }
```

### 3.2 Collector device

```json
{
  "type": "auth",
  "role": "collector",
  "token": "...",
  "device_id": "esp32-001",
  "device": {
    "name": "ESP32-001",
    "device_type": "esp32",
    "capabilities": ["bluetooth", "wifi"]
  }
}
```

The server verifies the token and that it is assigned to the same `device_id`. A token
cannot impersonate another device. Tokens are revocable and rotatable without changing
the device ID.

Invalid or missing credentials receive an `error` message and the connection is closed.
Tokens must never be written to ordinary logs.

## 4. Device registration and discovery

After collector authentication the server stores the device metadata and broadcasts a
fresh list to consumers:

```json
{
  "type": "device_list",
  "devices": [
    {
      "device_id": "esp32-001",
      "name": "ESP32-001",
      "device_type": "esp32",
      "capabilities": ["bluetooth", "wifi"],
      "online": true,
      "last_seen": 1755745200123,
      "last_data": 1755745200000
    }
  ]
}
```

`online` is based on heartbeat/last-seen timeout, not only TCP state.

## 5. Consumer subscription

```json
{ "type": "subscribe", "device_id": "esp32-001", "data_types": ["bluetooth", "wifi", "cell"] }
```

The server responds with the latest cached data for matching types, if available, then
pushes future updates:

```json
{
  "type": "environment_data",
  "device_id": "esp32-001",
  "data_type": "bluetooth",
  "timestamp": 1755745200123,
  "sequence": 18291,
  "data": { "raw": "...", "devices": [] },
  "cached": false
}
```

`unsubscribe` has the same shape as `subscribe`. A consumer changing device must first
unsubscribe from the old device; the Android manager also clears the old provider state
before applying the new device.

## 6. Heartbeat

The server sends WebSocket ping frames. Clients must answer with pong frames using the
WebSocket implementation's native ping/pong support. Clients may additionally send:

```json
{ "type": "heartbeat", "timestamp": 1755745200123 }
```

The server replies with:

```json
{ "type": "pong", "timestamp": 1755745200123, "server_time": 1755745200124 }
```

Collectors and consumers reconnect with bounded exponential backoff and re-authenticate.
The Android client restores its previous device subscription after receiving a new
`device_list`.

## 7. Collector upload

```json
{
  "type": "environment_data",
  "version": 1,
  "device_id": "esp32-001",
  "data_type": "wifi",
  "timestamp": 1755745200123,
  "sequence": 10,
  "data": {
    "raw": "base64-or-vendor-json",
    "networks": [
      { "ssid": "lab", "bssid": "AA:BB:CC:DD:EE:FF", "rssi": -54, "frequency": 2412 }
    ]
  }
}
```

The server validates envelope fields, device ownership, payload size, data type syntax,
sequence monotonicity, and per-device rate limits. It stores the latest envelope and
forwards it to subscribed consumers. Unknown data types are accepted if their identifier
is valid; the data object remains opaque.

## 8. Errors

```json
{
  "type": "error",
  "code": "invalid_token",
  "message": "authentication failed",
  "retryable": false
}
```

Defined codes include `unauthorized`, `invalid_token`, `invalid_message`, `unknown_device`,
`rate_limited`, `payload_too_large`, `sequence_rejected`, and `server_busy`.

## 9. Security and limits

- No anonymous collector upload.
- Tokens are generated with a cryptographically secure random source.
- Token values are shown only at explicit creation/rotation time and are stored hashed.
- Device ID and token are separate fields and separate database concepts.
- Recommended deployment is behind TLS termination with `wss://`.
- Per-device upload rate and payload size are bounded.
- Server logs contain token fingerprints or token IDs, never token material.
